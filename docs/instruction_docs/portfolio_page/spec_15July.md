BOOK ARCHITECTURE — READ THIS BEFORE ANYTHING ELSE ON THE PORTFOLIO SECTION. There are two separate levels of switching on this section, and they must never be confused with each other in the build.
UPPER LEVEL — the BOOK selector, sitting above everything else on the page: MODEL / BROKERAGE / PERSONAL. This chooses which portfolio you are looking at, and the three never share a ledger, a computed field, or a chart series:

MODEL — the full simulated portfolio (up to 179 assets, multi-currency, FX-converted to USD). This is the track record: every backtest, the sizing-overlay comparison, everything shown to prospective investors comes from here.

BROKERAGE — the real Interactive Brokers account. US-listed, USD-denominated only, by design — no FX, no currency risk. IBKR is the source of truth for this book: NAV, positions, and profit-and-loss come directly from the IBKR API. The frontend never computes anything for this book; it displays what IBKR reports.

PERSONAL — Rohit's own multi-currency holdings, entered manually (ticker + shares, or a starting valuation which the system converts to an implied share count at the current price; cost basis and entry date optional but recommended). FX-converts to USD; NAV and the chart update from the live price feed like any other book.

Because these three must never cross-contaminate — especially BROKERAGE, which is client-facing — every endpoint takes a book_id parameter (model | brokerage | personal), and no query, join, or display may ever mix them. Build three fully separate data-fetch paths, not one path with a filter.

LOWER LEVEL — the four-way valuation toggle (BASE / BASE+SSI / BASE+CONVICTION / ENHANCED — PRODUCTION SETTINGS) — renders ONLY inside MODEL, nowhere else. Reason: this toggle answers "what would this same set of trades look like under different sizing rules?" — a question that only makes sense where sizing is a simulated choice. BROKERAGE has no such choice to show (eg a brokerage firm like IBKR reports one real number, not variants); PERSONAL is not sized by SSI or Conviction at all, so the variants would be meaningless there, not merely unavailable. Note the renamed fourth option: what was "ENHANCED · LIVE" in earlier drafts is now "ENHANCED — PRODUCTION SETTINGS," to avoid any collision with the upper-level BROKERAGE book — the word "live" must not appear at two levels meaning two different things.

DATA SOURCES. Everything comes from FastAPI. The frontend never computes a size, a weight, a date, or an attribution number — ever. This is set up on purpose to protect your side: if a formula or a number changes, it changes in Divyanshu's endpoint and your components simply re-render — no frontend rework. Endpoints (Divyanshu providing; data shapes match the prototype's mock objects, all scoped by book_id where relevant): /portfolio/nav?book_id=model|brokerage|personal&book=base|ssi|cv|enhanced (book= only applies when book_id=model) — daily NAV series, closed-only and MTM variants, plus benchmark (S&P 500) series and realized vol / beta / best-worst month. /portfolio/sizing?scenario=normal|stress|lowvol|manual|auto — per-position sizes plus sleeve totals (true weight, ceiling, slots used/available) — MODEL book only. /portfolio/holdings?book_id=… — score, rank, R:R dynamic, hold-time-used %, conviction tier, sleeve, size per book; pnl_contribution per position; a same_asset_siblings array (populates for every position and signal, both directions — drives the chips in section 4); a multi_sig[] array (agreeing signals — drives the clickable MULTI-SIG chip); an exit_ref string (single nearest exit reference, e.g. "avg-gain target $257.25 — HIT · max exit Jul 16"). /signals/entries and /signals/exits — exits carry exit_type (signal | rr | eviction) and the cross-function conflict payload (triggering function, exit price and date, every remaining leg with MTM and implied natural exit date). alerts.json — type and target_page fields, for the slide-in.

AGENT SLIDE-IN (cross-page; notes demo shared in the past in detail). React fetches alerts.json once per page load. On the alert's target page: the OVERWATCH · AUTO-TRIGGERED panel slides in from the right after 1.5 seconds, with a dismiss ✕ and an action link. On any other page: no auto-open — red badge dot on the floating 💬 button only. A dismissed alert never auto-opens again in the same session.
PLACEHOLDERS. Every number in the prototype is illustrative. Bind to endpoints, never hardcode. Production drops the "illustrative" footer line once live data flows.
